# 关于"固件运行时长按 EC11 弹出菜单"的可行性分析

> 需求复述：在两个闭源固件（Bright-Heart / zhang-chong）**正在运行**时，长按 EC11 编码器 2 秒以上，弹出一个只有两个选项的菜单——"重启"和"默认固件"。
>
> 结论先行：**纯软件做不到；加装一颗廉价小 MCU 可以做到功能等价的替代方案。**

---

## 1. 先看启动链路：每一段归谁掌控

ESP32-S3 从上电到固件运行，是一条单向链路：

```
① ROM bootloader（芯片固化，只读）
        ↓ 读取 strapping 引脚 + flash 头
② 二级 bootloader（0x0，源码在我们手里，已定制）
        ↓ 读分区表(0x8000) + otadata(0xe000) + 复位原因
③ 选中 app 分区（factory 菜单 或 ota_0/ota_1 固件）
        ↓ 跳转入口，bootloader 生命周期结束
④ app 独占运行（固件 = 闭源二进制，我们无法插手）
```

关键点在第 ③→④ 步：**bootloader 是一次性的**。它跳进 app 之后，代码就从内存里消失了，CPU 归 app 的运行时（ESP-IDF / Arduino 的 FreeRTOS）全权接管。app 一直运行到下一次复位或断电。

这就是整件事的硬边界：**能弹菜单的"我们的代码"，只在第②（bootloader）和第③（factory 菜单）阶段活着；而需求要求它在第④阶段（固件运行中）响应按键。**

---

## 2. 为什么纯软件方案不可行

三个约束，任何一个单独就足以否定纯软件路径：

### 2.1 没有代码在监听

"长按 2 秒"不是一个硬件中断事件，它是**一段持续采样的结果**——需要有一个循环不断读 GPIO21 的电平、计时、判断阈值。这段代码必须"活着"才存在。固件运行期间，我们的菜单 app 已经不在执行，bootloader 也不在。没有任何我们的代码在跑，自然无从检测。

### 2.2 按键事件归当前 app 所有

GPIO 中断向量、输入 GPIO 的配置，都由当前运行的 app 设定。EC11 的 SW（GPIO21）在两个闭源固件里大概率已经被占用（切台、确认、静音之类）。即便我们能用某种方式读到电平，也没有合法途径"截获"这个事件——它属于固件。

### 2.3 回到我们的代码只有一条路：复位

从运行中的 app 回到 bootloader，唯一机制是**复位**。而复位会清空 RAM：固件当前的电台频率、音量、网络状态全部丢失。ESP32 的 RTC memory 能跨软件复位保留少量数据，但无法"冻结并恢复"一个完整的 FreeRTOS app。所以即使用 GPIO 唤醒或看门狗制造复位，也只是"重启"，不是"弹出一个叠加在固件之上的菜单"。

---

## 3. 二进制 patch（逆向注入）行不行？

理论上，ESP32-S3 的 app 是 ELF 转换来的 bin，运行时从 flash 取指执行（XIP），可以反汇编、找 hook 点、注入代码。理论上可以在固件里找到 GPIO21 的读取点，插入长按计时逻辑，再调用固件自己的绘图函数弹出菜单。

但工程上这条路实际走不通：

| 障碍 | 说明 |
|---|---|
| 无符号表 | 两个固件都是 strip 过的发布版，函数没有名字，纯靠反汇编猜 |
| 两套固件 | Bright-Heart 和 zhang-chong 结构完全不同，要各逆向一遍 |
| GUI 调用约定 | 要复用固件的界面绘制，得还原参数传递、帧缓冲地址、字体结构，难度极高 |
| 完整性校验 | 固件若启用 app 校验或 secure boot，任何字节改动都会导致启动失败 |
| 变砖风险 | patch 出错 =  bootloop，只能重新烧录恢复 |
| 授权问题 | 对闭源固件做逆向修改，可能违反其许可条款 |

**结论：理论存在，工程不可行，不建议。**

---

## 4. 可行路径：外加一颗小 MCU（功能等价方案）

核心思路：**既然从 app 内部出不来，就从硬件层面制造一次复位，让流程回到我们掌控的 bootloader。**

```
EC11 SW ──┬──→ ESP32-S3 GPIO21（原样，固件照常用）
          └──→ 小 MCU 输入脚（高阻监测，不干扰）

小 MCU 持续监测：
  短按  → 不动作，固件无感
  长按2s → 拉低 ESP32-S3 的 EN 脚 ≥ 100ms
                ↓
          硬件复位 → 冷启动 → 定制 bootloader
                ↓
          进 factory 菜单 → 选"重启"或"默认固件"
```

### 为什么这样能work

- **不改闭源固件**：一个字节都不动，规避所有逆向风险。
- **弹出的菜单由我们掌控**：既然"重启"和"默认固件"这两个操作本来就属于 bootloader 层（选分区、写 otadata、复位），菜单完全可以由我们写，不需要固件配合。
- **复位原因吻合**：EN 脚复位属于外部复位，我们定制的 bootloader 判断逻辑是"非 CORE_SW / CPU0_SW 一律进 factory 菜单"，所以长按复位后必然回到菜单。

### 硬件清单

| 元件 | 建议 | 说明 |
|---|---|---|
| 小 MCU | CH32V003 / ATtiny85 / ESP32-C3 | 几毛到几块钱，SOT-23-6 或 SOIC-8 |
| 连接 | 2 根信号线 + 供电 | SW 并联采样、EN 控制，从板上 3.3V 取电 |
| 固件 | 十几行代码 | 长按计时 + 拉低 EN |

### 软件侧要补的

菜单 app 里增加两个选项：

- **重启**：重新启动当前正在运行的固件（本质就是 `esp_restart()`，软件复位后 bootloader 按 otadata 回到该固件）。
- **默认固件**：把当前选择写进 NVS 作为默认项，然后启动；以后每次冷启动菜单默认高亮它。

注意一个语义问题：你上一条要求"每次断电开机都进菜单、记住上次选择"。如果"默认固件"还希望"开机跳过菜单直接进"，那就和这条要求冲突，需要重新定规则（比如加一个硬件拨动开关，或者菜单里再设一个"跳过菜单"的开关）。

### 备选：纯 RC 延时电路

不用 MCU，用电阻电容 + 三极管做 2 秒延时触发 EN 复位。成本更低，但延时精度受元件误差和温度影响大，抗干扰差，长按阈值不好调。**不推荐。**

---

## 5. 方案对比总结

| 方案 | 能实现需求？ | 改动量 | 风险 | 推荐度 |
|---|---|---|---|---|
| 纯软件（固件运行时监听） | 不能 | 无 | — | ✗ 不可行 |
| 二进制 patch 固件 | 理论能 | 极大 | 变砖 + 授权 | ✗ 不建议 |
| 长按回到启动菜单（小 MCU） | 功能等价 | 小（加一颗芯片） | 低 | ✓ 推荐 |
| 只在开机菜单里做长按工具页 | 部分（不能听广播时呼出） | 小（纯软件） | 无 | ○ 可接受折中 |

---

## 6. 建议的下一步

1. 确认"默认固件"的准确语义：是"菜单默认高亮"还是"开机跳过菜单"。
2. 若接受硬件方案，我可以把菜单 app 里的"重启 / 默认固件"两个选项先写好、编译、放进 Release；硬件部分给出接线图和 MCU 源码。
3. 若暂时不想动硬件，可以先做"开机菜单长按工具页"这个纯软件折中版本。
